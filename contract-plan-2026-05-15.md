## Goal and Confirmed Decisions

Replace the `generation_schema + sample_data.services` target with the BE-aligned tenant provisioning manifest. The AI will emit a compact manifest selecting BE-provided catalog IDs, customizing only confirmed tenant info. The BE service expands these IDs into queues, tickets, projects, dashboards, widgets, KPI bindings, and HR data.

- **Source of truth:** Use Vadim's `tenant_provisioning_*.jsonc` as the target contract shape.
- **Schema version:** Emit `schema_version: "2.0"`.
- **Name fields:** Include `name` beside IDs for readability; IDs are authoritative.
- **Dashboard key:** Use `dashboard`, not `dashboards`.
- **HR Hub key:** Emit `hr_hub`; BE aliases `hrHub`.
- **Murad schema:** BE aligns internally; AI doesn't emit Murad's OpenAPI shape.
- **Catalog data:** Do not manually insert queue/project/dashboard/ticket/widget/KPI data.
- **AI mutable surface:** Tenant info, selected IDs, and employee metadata.
- **Transport:** Direct — no wrapper. Manifest is the payload.
- **API field name:** `v2_manifest` (temporary during transition; field is removed post-migration when legacy fields are dropped).
- **`generated_at`:** Generated by AI alongside `session_id`.
- **Catalog ID stability:** BE catalog IDs are stable across environments. No environment-specific mapping needed.
- **Handoff endpoint:** `/app` endpoint. Final payload emitted by `/app` must be plug-and-play into the BE translator.
- **No rollback:** This migration is a one-way cutover. No rollback strategy is in place — legacy fields remain until Phase 8, after which the old contract is gone.

## AI Decisions and Restrictions

The AI determines:

- **Tenant:** company name, industry, size band, primary region, locale, timezone.
- **Tickets:** queue catalog IDs, names.
- **Projects:** project catalog IDs, names.
- **Dashboard:** dashboard catalog IDs, names.
- **KPI:** KPI catalog IDs, names.
- **HR Hub:** request type catalog IDs, names; employee catalog IDs, position, team, department, job title, job type, job level.

AI **DOES NOT** generate:

- Queue icons, emails, members, managers, categories.
- Tickets inside queues.
- Project leads, teams, start dates, tasks.
- Dashboard widgets, layouts, flags, KPI bindings.
- KPI formulas, definitions, display behavior.
- HR request workflow behavior.
- Frontend-only dashboard widget stores.
- Legacy `dummy_data_json.stores`.

1. **Dashboard widget store leak:** Separation of preview-only vs BE handoff fields is explicit. Dashboard enrichment files are FE preview scope only — do not include widget/layout data in v2 manifest.
2. **Edit flow hard cutover (Phase 5):** No dual-write. Confirm with team that nothing downstream depends on legacy `apply.py` behavior before cutting over.
3. **Frozen-catalog assertions:** Existing tests assert on legacy shape. Must split fixtures (Phase 2) before Phase 3 or integration tests will break.
4. **`AppPayloadContract` gate:** Addressed in Phase 1. `contract.py` must be updated before Phase 3 attempts to pass v2 manifest through it.
5. **`preview_flow.py` bypasses `AppGeneratorService`:** It constructs `AppPayload` directly. Phase 3 must wire v2 manifest into this direct-construction path or it will be silently skipped.
6. **`CanonicalPayloadBuilder` is a bridge, not the v2 emitter:** CJ's Phase 2 work converts manifests → legacy stores. This is a transition vehicle. Phase 3 must add direct manifest emission alongside (not instead of) this bridge until Phase 8.
7. **Dual `GenerationJSON`/`DummyDataJSON` schema definitions:** `src/generator/schemas.py` and `src/agents/preview_generator/schemas.py` define incompatible shapes. The `src/generator/` module appears orphaned. Verify before Phase 8 removal.
8. **`bundle_registry.yaml` alignment:** Has an open TODO about alignment with new canonical contract. Must be resolved in Phase 2 alongside CJ's registry work.
